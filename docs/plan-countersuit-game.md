## Context

## 단계와 순서

```

  └─> 1단계 혼자 변론 게임                (맞고소 확인 3건 후)
```

## 1단계: 혼자 변론 게임 (적용 완료 → 2026-11-04 반박 카드 게임으로 교체)

> **현재 동작은 반박 카드 게임이다.** 아래의 반응 속도(타이밍) 설계는 2026-11-03에 적용했다가, '의미불명에 재미없다'는 사용자 의견으로 2026-11-04 교체한 기록이다.
>
> - 궤변 3개(사건 항변·맞고소 죄목·사유)마다 반박 카드 3장 중 맞는 것을 고른다. 정답은 시나리오의 배척 판시(`defense.rejection`)와 새로 쓴 맞고소 죄목·사유별 반박(`COUNTER_CRIME_REBUTTALS`, `COUNTER_CLOSER_REBUTTALS`)이고, 오답은 다른 사건의 판시와 다른 반박에서 뽑는다(`generateCounterRounds`).
> - 맞힐 때마다 '재판부 마음' 게이지가 찬다. 결과는 맞힌 수로 정한다: 2장 이상(원심이 무죄·훈방이면 3장 모두)이면 기각(`counterNeeded`). 건너뛰기는 예전 확률(`SKIP_ACCEPT_CHANCE` 0.7/0.15)이다.
> - 화면은 고른 카드 위치(`picks`)만 보내고, 서버가 맞힌 수와 결정적 반박(처음 맞힌 반박)을 다시 계산해 맞고소장 변론 기록에 남긴다.
> - 타이밍 게임용 확률표·판정 창 규칙은 더 이상 쓰지 않는다.

**착수 조건:** 동료 공유 뒤 맞고소 확인이 3건 이상일 때. 본인 테스트는 제외한다. 2026-11-03 사용자 요청으로 조건 확인 없이 적용했다.

적용 시 정한 세부: 2라운드 문장은 죄목이 모두 '죄'로 끝나 `{죄목}를 범했습니다`로 쓴다. 빨개지는 끝부분은 마지막 어절(4자 미만이면 앞 어절까지)이다. 판정 규칙은 `frontend/src/domain/countersuit-game.ts`, 확률표는 `backend/src/domain/documents.ts`의 `COUNTER_ACCEPT_CHANCE`가 단일 원본이다. 엔터 키도 스페이스와 같이 받는다.

```sql
SELECT count(*) FROM lifecourt.cases
WHERE countersuit IS NOT NULL AND created_at >= '<공유 시작 시각>';
```

### 사용자 흐름

1. `/countersuit` 진입 시 결과가 없으면 자동 접수하지 않고 시작 화면을 보여준다.
   `적반하장입니다. 피고 측이 오히려 맞고소장을 냈습니다. 궤변이 빨개지면 이의를 제기하세요.`
2. 버튼은 `변론 시작`, `건너뛰기` 두 개다.
3. 3라운드 동안 문장이 글자당 40ms, 최대 2.2초로 나오고 끝부분이 빨개진다.
4. 라운드마다 `이의 있음!`을 한 번 누를 수 있다. 판정 후 0.7초 뒤 다음 라운드로 넘어간다.
5. 끝나면 결과를 저장하고 기존 결과 화면을 보여준다. 결과 문구는 기각 `적반하장 진압 완료`, 인용 `적반하장이 통했습니다. 아래 벌칙을 이행하세요`를 추가한다. 인용 벌칙은 `COUNTER_PENALTIES` 12종 중 하나다(2026-11-03, 늘 '음료 1잔'이던 것을 바꿨다).

| 라운드 | 문장 | 판정 창 |
|---|---|---|
| 1 | 사건 시나리오의 `defense.claim` | 700ms |
| 2 | `피맞고소인은 {맞고소 죄목}을 범했습니다` | 500ms |
| 3 | 맞고소 사유 문구 `COUNTER_FACT_CLOSERS` | 350ms |

판정 창은 처음 1000/800/600ms로 배포했으나, 집중하면 누구나 다 막아 점수가 결과를 가르지 못해 2026-11-03에 줄였다. 판정 창이 열리면 문장 끝과 함께 버튼도 번쩍인다(동작 줄이기 설정에서는 밝은 테두리만).

| 누른 시점 | 결과 | 표시 |
|---|---|---|
| 판정 창 안 | 성공 | `Sustained!` |
| 판정 창 전 | 실패, 라운드 종료 | `Overruled!` |
| 누르지 않음 | 실패 | `이의 없으면 넘어갑니다.` |

- 입력은 `pointerdown`과 스페이스바, 진동 30ms를 쓰고 소리는 쓰지 않는다.
- `prefers-reduced-motion`이면 흔들림만 끄고 판정 창은 유지한다.
- 결과가 저장되기 전 새로고침하면 1라운드부터 다시 한다. 저장된 뒤에는 게임 없이 결과만 보여준다.

### 결과 규칙

성공 횟수별 맞고소 인용 확률이다. 건너뛰기와 `hits` 없는 요청은 1회로 처리해 현재 확률과 같게 한다.

| 성공 | 원심 무죄·훈방 | 그 외 |
|---|---|---|
| 0 | 0.80 | 0.25 |
| 1 | 0.70 | 0.15 |
| 2 | 0.55 | 0.08 |
| 3 | 0 (완벽 변론) | 0 (완벽 변론) |

3회를 모두 막고도 지면 납득하기 어려워 2026-11-03에 3회 행을 0.35/0.05에서 0으로 바꿨다. 결과 화면은 `완벽 변론! 적반하장 진압 완료`, 문서는 `… 3회 인용 — 완벽 변론`을 표시한다.

기존 난수 순서(인용 판단, 죄목, 사유 순)를 유지해 같은 사건은 같은 조건에서 같은 결과가 나오게 한다.

### API

```
GET /api/cases/:seq/countersuit/brief
헤더: X-Owner-Token
200 { "lines": [string, string, string] }
404 사건 없음 / 403 토큰 오류 / 결과가 이미 있으면 200 { "lines": [...], "done": true }

POST /api/cases/:seq/countersuit
헤더: X-Owner-Token
본문: { "hits"?: 0 | 1 | 2 | 3 }
200 { "countersuit": CountersuitDoc }
400 hits가 0~3 정수가 아님
```

```ts
interface CountersuitDoc {
  // 기존 필드 유지
  objections?: { hits: number; total: 3 };
}
```

- 값이 있으면 문서에 `변론 기록: 이의 제기 3회 중 {hits}회 인용`을 표시한다. 건너뛰면 표시하지 않는다.
- 저장은 `UPDATE cases SET countersuit = $2 WHERE seq = $1 AND countersuit IS NULL RETURNING seq`로 바꾼다. 실패하면 저장된 문서를 다시 읽어 돌려준다.
- 점수는 서버가 범위만 검사한다. 랭킹이 없어 조작해도 본인 결과만 바뀐다.

## 2단계: 같이 대결 (휴대폰 한 대)

피고 쪽 게임의 첫 단계다. 서버로 다른 사람과 주고받는 것이 없고, 원고 세션 안에서 끝난다.

1. 시작 화면에 `피고가 옆에 있나요?`를 묻고 `혼자 변론`(기본), `같이 대결`을 고른다.
2. 원고가 궤변 3개를 막은 뒤 `휴대폰을 피고에게 넘기세요` 화면을 보여준다.
3. 피고가 원고의 과장된 진술 3개를 막는다. 판정 창과 규칙은 같다.
4. 성공 횟수가 많은 쪽이 이긴다. 원고가 이기면 맞고소 기각, 피고가 이기면 `적반하장 인용`이다.
5. 비기면 원고 성공 횟수로 1단계 확률표를 적용한다.
6. 문서에 `변론 대결 {원고} : {피고}`를 표시한다.

피고 문장은 서버가 만든다. 원고 세션이므로 사연 발췌를 쓸 수 있다.

| 라운드 | 문장 |
|---|---|
| 1 | `"{사연 발췌}"라는 진술은 상당히 각색되었습니다` |
| 2 | `원고는 본인 지분을 빼고 진술했습니다` |
| 3 | `이 사건은 친구끼리 말로 끝낼 일이었습니다` |

API 변경은 `brief`에 `defendantLines`를 추가하고, `POST` 본문에 `{ "duel": { "plaintiff": 0~3, "defendant": 0~3 } }`를 허용하는 것이다. `hits`와 `duel`을 함께 보내면 400이다.

## 3단계: 피고 출석 (설계 시작)

실제 피고가 공유 링크로 참여하는 쌍방 확장의 첫 형태다. **실시간 대결이 아니라, 원고가 남긴 점수에 피고가 나중에 도전하는 비동기 방식**으로 설계한다. 원고 토큰이 탭과 함께 사라지고 알림 수단이 없어서, 두 사람이 동시에 접속하거나 원고가 돌아와야 하는 구조는 완주되지 않는다.

**착수 조건:** 답변서 제출이 3건 이상일 때. 공유 링크를 받은 사람이 실제로 움직인다는 근거다.

### 흐름

1. 원고가 1단계를 하면 `objections.hits`가 남는다. 안 했으면 기준 점수는 1이다.
2. 피고가 `/s/` 링크에서 답변서 아래 `법정 출석하기`를 누른다.
3. 피고가 3라운드 게임을 하고, 서버가 원고 기준 점수와 비교한다.
4. 같은 링크에 `출석 기록`이 표시된다. 피고 승리는 `적반하장 인용`, 패배는 `출석 후 기각`, 동점은 `쌍방 화해 권고`다.
5. 원고는 같은 공유 링크를 다시 열어 확인한다. 공유 화면에 `이 링크에서 피고의 출석 결과를 볼 수 있습니다`를 안내한다.

### 데이터와 API

```sql
ALTER TABLE cases ADD COLUMN IF NOT EXISTS appearance JSONB;
```

```ts
interface DefendantAppearance {
  hits: number;              // 0~3
  plaintiffHits: number;     // 저장 시점 원고 기준 점수
  outcome: "defendant" | "plaintiff" | "draw";
  at: string;                // ISO 시각
}
```

```
GET  /api/cases/:seq?t=...
     기존 응답에 appearance, appearanceLines 추가

POST /api/cases/:seq/appearance
본문: { "t": 공유토큰, "hits": 0~3 }
201 { "appearance": DefendantAppearance }
409 이미 출석함. 기존 appearance를 함께 반환
403 토큰 오류 / 400 hits 오류
```

저장은 `UPDATE ... WHERE seq = $1 AND appearance IS NULL RETURNING seq`로 선착 1회를 보장한다.

### 설계 규칙

- **원심 불변:** 답변서와 같이 부가 기록이다. 판결문과 맞고소 문서는 바꾸지 않는다.
- **자유 텍스트 없음:** 입력은 점수뿐이라 금칙어 필터가 필요 없다.
- **입력 원문 비노출:** `appearanceLines`는 공유 화면에 이미 공개된 판결 필드(`crime`, `order`, `result`)와 고정 문구로만 만든다. 2단계의 사연 발췌 문장을 재사용하지 않는다.
- **권한:** 공유 토큰으로 제출한다. 링크가 전달되면 다른 사람도 출석할 수 있는 점은 답변서와 같다.
- **예고 문구:** 3단계 배포 시 0단계의 `가상 연출` 문구를 실제 출석 기능과 구분되도록 고친다.

### 3단계 착수 전 결정할 것

1. 출석 결과를 원고에게 알릴 방법을 만들지. 현재 설계는 링크 재방문뿐이다.
2. 출석 결과를 공유 카드(OG)에 표시할지. 표시하면 확산에 좋지만 결과가 대화방에 노출된다.
3. 고지문을 어떻게 고칠지. 출석 기록의 보관과 표시 범위를 안내해야 한다.

## 향후 후보: 이용자가 벌칙 고르기

2026-11-03 사용자 제안. 원고가 판결 뒤 벌칙(예: 벌금형·봉사형·칭찬형)을 직접 골라 부과하는 기능이다.

- 처음에는 자유 입력 없이 준비된 선택지에서만 고른다. 금칙어 필터를 우회할 입력란을 만들지 않기 위해서다.
- 자유 입력을 연다면 `backend/src/domain/moderation.ts`의 같은 검사를 서버에서 거치고, 큰 금액·신체적 위험·망신을 요구하는 내용을 막는 규칙을 먼저 정한다.
- 착수 조건과 화면 위치(판결 직후 또는 상고 이후)는 착수 시 정한다.

## 향후 후보: 변호사·검사는 사람, 판사는 AI

2026-11-04 사용자 아이디어. 원고(검사 역)와 공유 링크를 받은 친구나 피고(변호사 역)가 주장 카드를 하나씩 내고 판사가 판결한다.

- 지금 판사는 AI가 아니라 규칙·템플릿이다. 규칙 판사로 만들면 'AI 판사'라고 부르지 않는다(예: 자동 재판부).
- 실제 AI(예: Claude API)를 쓰면 사연을 이해한 판결 문장이 가능하지만, 착수 전에 정할 것이 있다: 호출 비용 상한, AI 출력의 금칙어 검사, 사연 속 지시문(프롬프트 주입) 대응, 응답 지연, 같은 입력에도 결과가 달라지는 점, 고지문의 'LLM 미사용' 설명 변경.
- 사용자 결정(2026-11-04): 배심원제를 먼저 만들고, AI 판사는 참여 반응을 본 뒤 비용과 안전장치를 정해 시험한다.

## 향후 후보: 실제 맞고소, 피고 항소

2026-11-03 메모판에 '운영자 아이디어'로 공개한 항목이다. 착수 전 설계가 필요하다.

- **실제 맞고소**: 지금 맞고소는 원고 화면의 가상 연출이다. 실제 피고가 공유 링크로 맞고소하려면 3단계(피고 출석)의 공유 토큰 권한·선착 저장·고지문 정비를 먼저 갖춘다. 자유 텍스트를 열면 금칙어 검사를 서버에서 거친다.
- **피고 항소**: 지금 항소·상고는 원고만 한다. 피고 항소를 열면 처분이 가벼워질 수 있으므로 원고 항소와 같은 사건에서 순서·확정 규칙(누가 먼저, 상고 뒤 확정과의 관계)을 정해야 한다. 원심과 저장된 판결은 바꾸지 않고 부가 기록으로 남기는 방식을 우선 검토한다. 실제 형사소송법 제368조(불이익변경의 금지)처럼, 피고가 항소한 경우에는 원심보다 무거운 처분을 내리지 않는다(2026-11-03 조문 확인, 법제처 국가법령정보센터).

### 실제 절차와의 차이 (2026-11-03 검토)

오락용 패러디라 그대로 두되, 바꿀 때 참고한다.

- 처분 사다리 '훈방 조치'는 법원 판결이 아니라 경찰 단계의 재량 처리다. 법원 판결 중 가장 가벼운 유죄 쪽은 선고유예(형법 제59조)다.
- '조건부 유죄'는 실제 용어가 아니다. 가장 가까운 것은 집행유예(형법 제62조)이며 보호관찰·사회봉사·수강명령을 붙일 수 있다(제62조의2).
- '괘씸죄 가중'은 없다. 실제 가중은 누범 가중(형법 제35조, 장기의 2배까지) 등이다.
- 형사 사건의 상소권자는 검사 또는 피고인(형사소송법 제338조)이다. 이 앱의 '원고 항소'는 검사 항소에 가깝고, 원고·피고는 민사 용어다.
- 상고(형사소송법 제371조)의 이유는 법령 위반 등으로 제한되며(제383조), 대법원은 보통 직접 형을 정하기보다 파기환송한다.
- 이름을 실제에 가깝게 바꾸면(예: 훈방 조치→선고유예, 조건부 유죄→집행유예) 저장된 판결의 처분명이 사다리에서 사라지므로, 예전 이름을 새 이름으로 읽는 대응표를 먼저 만든다.

## Acceptance Criteria

### 0단계

1. 판결 화면 알림과 맞고소 문서, 저장 이미지에 가상 연출임이 표시된다.
2. 예고 문구는 맞고소 결과 화면에만 나오고 첫 화면과 `/invite`에는 없다.
3. 고지문 제2조가 사용자 공유 링크를 예외로 명시한다.

### 1단계

4. 결과가 없는 사건은 `/countersuit` 진입만으로 맞고소가 저장되지 않는다.
5. 건너뛰기와 `hits` 없는 요청의 결과가 변경 전 확률표와 일치한다.
6. 성공 횟수별 확률이 표와 일치하고, 같은 사건·같은 `hits`는 같은 결과를 낸다.
7. 범위 밖 `hits`는 400이다. 토큰 오류는 403이고 게임 문장도 반환하지 않는다.
8. 동시 요청 10건을 보내도 저장된 문서는 하나이고 모든 응답이 그 문서를 반환한다.
9. 저장 후 다시 진입하면 게임 없이 같은 결과가 나온다.
10. 빠른 입력, 창 안 입력, 입력 없음이 각각 `Overruled!`, `Sustained!`, 놓침으로 판정된다.
11. 게임 화면에서 375×560, 360×640, 390×664 크기 모두 버튼이 스크롤 없이 보인다.

### 2단계

12. `같이 대결` 선택 전에는 기존 혼자 변론과 같게 동작한다.
13. 양쪽 성공 수가 다르면 많은 쪽이 이기고, 같으면 1단계 확률을 쓴다.
14. `hits`와 `duel`을 함께 보내면 400이다.

### 3단계

15. 공유 토큰 없이는 제출할 수 없고, 응답에 입력 원문과 접수자 토큰이 없다.
16. 동시 제출 시 한 건만 201이고 나머지는 409와 저장된 결과를 받는다.
17. 출석 뒤에도 `verdict`, `countersuit`, `response` 값이 바뀌지 않는다.
